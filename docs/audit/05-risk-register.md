# 05 · 风险登记册

分级：**P0** 阻断/高危 · **P1** 影响进度或质量 · **P2** 需关注 · **P3** 记录备查

| ID | 风险 | 等级 | 证据 | 影响 | 建议动作 |
|---|---|---|---|---|---|
| R01 | **零测试覆盖** | P0 | 无 `src/test` 目录，0 个 `*Test.java` | 任何重构都无法验证回归；多平台改造必然引入静默破坏 | P1 阶段先补「评论入库幂等」「AI 结果落库」「报告导出」三条冒烟测试 |
| R02 | **实体与库表漂移** | P0 | V8 迁移即因实体有 `sourceLevel`、建表遗漏导致整批评论 FAILED | 同类问题会在新增字段时重复发生 | 把「实体字段 ↔ information_schema」比对纳入 CI（已有 `tools/check_schema_drift.py` 可改造复用） |
| R03 | **单平台硬编码** | P0 | `video.aweme_id`、`comment.cid/dedup_key`、`AiAnalysisService` 内 `provider="deepseek"` 均写死 | 多平台改造要动核心表与核心服务，成本最高 | 先加 `source_id` 默认 1（DOUYIN），不改语义只加维度 |
| R04 | **关键词搜索未验证** | P1 | `douyin_search.py` 存在但从未跑通 | 若排进 P1 交付会直接卡住 | 单独立项做可行性验证，**不与 Adapter 交付捆绑** |
| R05 | **`file_asset` 空壳** | P1 | 表已建，**0 个 Java 文件引用** | 容易被误认为「已实现」，实际无任何上传落库逻辑 | 要么补齐实现，要么在文档中明确标注「未启用」 |
| R06 | **`analysis_profile` 版本化未贯通** | P1 | 仅 3 个 Java 文件引用，`profileId` 仅 3 处使用；无 `prompt_version` / `model_config_id` 字段 | 无法「同一内容用不同规则重跑并对比」，这是 AI 评估体系的前提 | P3 阶段补字段与重跑接口 |
| R07 | **匿名采集产量低** | P1 | 实测约 3 页 / 15–20 条即止 | 线索量不足会直接削弱获客价值 | 必须在登录态下测试上限，并据此设定业务预期 |
| R08 | **权限模型过简** | P2 | `user.role` 仅一个整数，无角色表、无细粒度权限 | 商业化时无法做数据隔离 | 首期够用，商业化前重构；先预留 `tenant_id` |
| R09 | **双副本共享容器名与数据卷** | P2 | 两处 `docker-compose.yml` 均声明 `name: coolpilot-insight`，容器名 `cpi-*`、卷 `coolpilot-insight_*` | 两个副本不能同时启动；误在 A 项目 down/删卷会影响 B | 明确唯一开发副本；另一处改名或标记只读 |
| R10 | **AI 结果缺模型/Prompt 留痕** | P2 | `usage_record` 记了 provider/model/token，但 `comment_analysis`/`video_insight` 未存分析时用的 prompt 与模型版本 | 结果不可复现，无法做 A/B 与回归 | 在结果表加 `profile_version` / `model_config_snapshot` |
| R11 | **无多租户字段** | P3 | 25 表中无 `tenant_id` / `owner_user_id`（仅采集任务有 owner） | 未来商业化需大范围迁移 | 借新增表之机统一加，旧表暂不动 |
| R12 | **迁移不可回滚** | P3 | MySQL DDL 隐式提交，Flyway 无 down 脚本 | 迁移失败只能靠备份恢复 | 迁移前强制备份；禁止在业务高峰期执行 |

## 风险处置优先级

1. **R01 + R02**（测试与漂移检查）——不是功能，但是所有后续改造的地基，成本低、收益立竿见影
2. **R03**（单平台抽象）——决定改造路线，越早定越省事
3. **R07 + R04**（产量与关键词）——决定这个产品能不能成立，属于**业务可行性**而非技术风险
4. 其余按交付阶段顺延

## 需要业务方确认的两个判断

- **R07 决定产品天花板**：如果登录态下也只能拿到几十条评论/视频，那么「发现需求」的样本量
  可能不足以支撑线索生意。这一点应该在 P1 之前用真实数据验证，而不是等系统建完再发现。
- **R04 决定 P1 范围**：关键词搜索是「发现」环节的入口。如果它不可用，
  数据源就退化为「已知 URL 采集」，产品逻辑要从「主动发现」改为「定向分析」——
  这是**产品定位级别**的差异，不是技术细节。
