## 2. 大量视频的批量采集能力

### 2.1 现状

| 维度 | 现状 | 等级 |
|------|------|------|
| 单次任务视频数 | 1（接口不支持数组） | D |
| 任务并发 | 裸线程无限创建 | D |
| Chrome 实例 | 共用单一 profile | D |
| 理论吞吐 | 每视频约 40~90 秒（实测 3 页约 30~60 秒） | A（实测） |

### 2.2 容量推演（**未测试**）

假设并发度 = 2（安全上限）：

```
每小时理论吞吐 = 3600 / 60 × 2 ≈ 120 个视频
每天 ≈ 2880 个视频
```

**但实际瓶颈不在调度，而在：**

| 瓶颈 | 说明 |
|------|------|
| Chrome 内存 | 每个 Chrome 实例约 300~500MB（实测单实例约 350MB）→ 并发 2 约 700MB~1GB |
| 抖音风控 | 匿名态单 IP 连续请求会被限流，实际吞吐远低于理论值 |
| profile 争抢 | 并发 > 1 必然冲突（实测 2/3 失败） |

**结论（未测试）**：当前架构**无法支撑多视频批量采集**。
需先解决并发安全（独立 profile 或串行），再谈吞吐。

### 2.3 建议目标

| 阶段 | 并发度 | 每日视频数 | 前提 |
|------|-------|-----------|------|
| 现状 | 1（且会冲突） | ~800（串行估算，未测试） | — |
| 修复并发后 | 2 | ~1600（未测试） | 每任务独立 profile |
| 目标态 | 3~4 | ~3000（未测试） | 任务表 + 限流 + 重试 |

## 3. 大量评论的存储能力

### 3.1 当前存储特征

| 特征 | 值 | 影响 |
|------|-----|------|
| 单条大小 | 昵称(100B) + 内容(~100B) + 标识(200B) + 其他 ≈ **500B~1KB** | — |
| 100 万条 | ≈ 500MB~1GB | ✅ MySQL 轻松承载 |
| 1000 万条 | ≈ 5~10GB | ✅ 需分表或归档 |
| 主键 | bigint AUTO_INCREMENT | ✅ |
| 内容类型 | TEXT | ⚠️ 行外存储，读取有额外 IO |

### 3.2 表结构对规模的适应性

| 问题 | 影响规模 | 等级 |
|------|---------|------|
| `comment` 无分区 | 1000 万条后 INSERT 变慢 | P2 |
| `analysis_result` 用 TEXT 存 JSON | 单行 JSON 可能达 MB 级（如 top_comments 存 20 条 × 500B = 10KB，尚可） | 低 |
| `getVideoList()` 全表扫描 + 内存去重 | **100 万条时 OOM 风险** | **P1** |
| 无归档/冷数据分离 | 历史数据永久在线 | P2 |

**关键问题**：`AnalysisServiceImpl.getVideoList()`：
```java
List<Comment> all = commentMapper.selectList(wrapper);   // 全表！
LinkedHashSet<String> seen = ...;                        // 内存去重
```
**100 万条评论 → 加载 100 万个 Comment 对象到堆内存 → 极可能 OOM**。

修复：改用 `SELECT DISTINCT video_id` + `COUNT(*)` GROUP BY，或建 `video` 表。

### 3.3 索引效率

| 查询 | 索引 | 效率 |
|------|------|------|
| `WHERE video_id=?` | `idx_video_id` | ✅ |
| `WHERE video_id=? AND user_id=?` | ⚠️ 无 `user_id` 索引 | **P2**（需回表过滤） |
| `WHERE video_id=? GROUP BY region` | `idx_video_region` | ✅ 覆盖索引 |
| `ORDER BY likes DESC LIMIT 20` + `video_id=?` | `idx_video_likes` | ✅ |
| `SELECT DISTINCT video_id` | `idx_video_id` | ✅（但当前未用 DISTINCT） |
| 情感趋势 `GROUP BY DATE(publish_time)` | `idx_video_time` | ⚠️ 函数包裹列，索引部分失效 |

## 4. 评论分页性能

| 场景 | 实现 | 评价 |
|------|------|------|
| 评论列表分页 | MyBatis-Plus `Page` + `LIMIT` | ✅ 标准做法，深分页（offset 大）会退化 |
| 深分页 | offset = page × size | ⚠️ 万级页码会全表扫描（可改游标分页） |
| 每页大小 | 固定 20，前端不可调 | ⚠️ 无法按需调整 |

**结论**：分页性能在万级数据内无问题，十万级以上需评估深分页。

## 5. AI 分析耗时与成本

### 5.1 耗时

| 环节 | 耗时 | 等级 |
|------|------|------|
| Java → Flask | < 1s | A |
| Flask jieba 分词 | 首次预加载 ~2s，之后 ~50ms/视频 | A |
| **Flask → DeepSeek** | **未实测**（timeout 设 30s） | E |
| Java → Flask 的 readTimeout | 30s | A |

**未实测项**：DeepSeek 实际响应时间。代码设了 30s 超时，
实际可能 3~15s（取决于输出长度与模型负载）。

**风险**：Java 侧 `readTimeout=30000` 与 Flask 侧 `timeout=30` **相同，无余量**——
若 DeepSeek 恰好在 30s 超时，Java 会先超时而 Flask 仍在等待，
产生"Java 认为失败、Flask 后成功"的资源浪费（AI 费用已产生但结果丢弃）。

**建议**：Java 侧 readTimeout 设为 45s（> Flask 的 30s + 网络余量）。

### 5.2 Token 成本

**当前实现**：LLM 只接收**聚合统计特征**（不含评论原文）。

粗略估算（**未实测，需按 DeepSeek 实际定价核对**）：

| 项目 | 输入 tokens | 输出 tokens |
|------|------------|-----------|
| 统计特征 + Prompt | ~800~1500 | ~1200~1800 (max_tokens=2000) |

单次核心话题分析 ≈ 2000~3300 tokens。

**当前成本很低**（因为传的是统计特征，不是原文）。
这也正是"AI 能力升级"的核心矛盾：**传原文才能做需求分析，但成本会上升 10~50 倍**。

### 5.3 升级后的成本预估（**未实测**）

若改为传评论原文（阶段 B 方案）：

| 数据量 | 分批 | 单次输入 tokens | 累计 tokens |
|-------|------|--------------|-----------|
| 100 条评论 | 2 批 × 50 | ~8000/批 | ~16000 |
| 320 条评论 | 4 批 × 80 | ~12000/批 | ~48000 |
| 1000 条评论 | 10 批 × 100 | ~15000/批 | ~150000 |

**必须配套**：增量分析（只处理新增）、结果持久化、Token 预算计数。
否则重复点击"刷新分析"会持续产生费用。

## 8. 系统异常恢复能力

| 场景 | 恢复能力 | 等级 |
|------|---------|------|
| 采集进程被杀 | ❌ 已采数据全丢（末尾落盘） | C |
| 容器重启 | ❌ 任务状态丢失，Token 失效（用户被登出） | C |
| MySQL 短暂不可用 | ❌ 采集失败即终止，无重试 | D |
| Flask 不可用 | ✅ AI 分析降级为统计报告（不影响其他功能） | A |
| DeepSeek 不可用 | ✅ 降级为统计报告 | A |

| 页面结构变化 | ✅ `preflight_check` 报错退出 | A |

**恢复能力综合评价**：**弱**。仅 AI 层有优雅降级，采集层无任何恢复机制。

## 11. 性能优化的优先级建议

```
立即（不改架构，收益最大）：
  1. getVideoList() 改 DISTINCT + GROUP BY       → 消除 OOM 风险
  2. comment.user_id 加索引                       → 消除普通用户全表扫描
  3. 采集并发上限 = 1（或每任务独立 profile）      → 消除任务互相踩踏
  4. 采集改 append 落盘                          → 消除中断全丢

短期：
  5. comment 加 cid + 唯一索引                     → 支撑增量与去重原子化
  6. 任务表 + 状态落库                             → 支撑恢复与统计
  7. AI 侧加 Semaphore 限流 + Token 计数 + 结果持久化 → 控制成本

中期（数据量增长后）：
  8. comment 分表或归档
  9. 游标分页替代深分页
  10. 趋势统计改用范围索引
```
