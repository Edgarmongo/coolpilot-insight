# 08 · AI_CAPABILITY_ROADMAP

> 下一阶段 AI 能力规划（仅设计，未实施）
> 目标定位：AI 驱动的社交媒体评论采集与用户需求分析平台

---

## 1. 现状与目标的差距（核心判断）

### 1.1 当前 AI 链路的本质

```
评论 → 聚合统计(5维度) → LLM → Markdown 报告
         ↑ 只有统计特征
```

LLM **从未看到评论原文**。这决定了当前架构的能力天花板：

| 能力 | 依赖原文？ | 当前可否实现 |
|------|-----------|------------|
| 数据摘要报告 | 否 | ✅ 已实现 |
| 用户需求识别 | **是** | ❌ 结构上不可能 |
| 用户痛点提取 | **是** | ❌ 结构上不可能 |
| 购买意向识别 | **是** | ❌ 结构上不可能 |
| 竞品优缺点 | **是** | ❌ 结构上不可能 |

**结论：不做架构调整，AI 能力无法从"报告生成"跃升到"需求洞察"。**

### 1.2 第二层差距：输出不可消费

当前输出是 Markdown 字符串。要支撑"竞品对比""行业热点""多视频联合分析"，
输出必须是**结构化 JSON**，能被程序聚合、比较、统计。

---

## 2. 四级分析粒度（任务卡要求明确区分）

| 层级 | 定义 | 输入范围 | 当前状态 | 所需基础设施 |
|------|------|---------|---------|-------------|
| **评论级** | 单条评论的意图/情感/主题 | 1 条评论 | ⚠️ 仅情感 | 无需新设施 |
| **视频级** | 单个视频的整体画像 | 1 个视频全部评论 | ✅ 统计 + 报告 | 需结构化输出 |
| **关键词级** | 某关键词下所有视频的横向对比 | N 个视频 | ❌ | 需 `video` 表 + 关键词表 |
| **行业级** | 跨关键词的趋势与洞察 | 大量视频 | ❌ | 需调度 + 定时 + 大数据量 |

**依赖链是自下而上的**：评论级 → 视频级 → 关键词级 → 行业级。
当前实现停在视频级，且输出格式限制了向上聚合。

## 3. 能力规划详述

### 3.1 评论级（基础能力）

#### 3.1.1 结构化评论分析

**目标**：单条评论输出结构化标签，替代/补充当前的三分类情感。

```json
{
  "comment_id": "7300000000000000000",
  "sentiment": {"label": "negative", "score": 0.82, "confidence": 0.76},
  "intent": ["complaint", "question_about_shipping"],
  "topics": ["价格", "物流", "客服态度"],
  "pain_points": ["配送太慢", "包装破损"],
  "purchase_intent": {"level": "high", "signals": ["已经下单3个", "求链接"]},
  "user_need": "希望有更大容量",
  "is_competitor_mention": false,
  "mentioned_products": ["竞品A"]
}
```

**实现要点**：

| 项 | 方案 |
|----|------|
| 调用方式 | Flask 侧新增 `/analyze_comments`，批量传入评论数组 |
| 批大小 | 建议 10~20 条/次（token 与准确率平衡） |
| 模型 | `deepseek-chat`，`temperature=0.1`（分类任务需确定性） |
| 输出约束 | **强制 JSON 输出**，配合 JSON Schema 或强约束 Prompt |
| 解析 | `response_format={"type":"json_object"}`（DeepSeek 兼容模式支持） |
| 校验 | Python 侧 `json.loads` + 字段完整性校验，失败重试 1 次 |
| 成本 | 单条约 150~300 tokens；1000 条 ≈ 20~30 万 tokens |

**与现有情感分析的关系**：
- 现有 SnowNLP 保留作为**低成本预筛**（先过滤明显中性/正面，只对模糊样本调 LLM）
- 这能省 60~70% 的 LLM 调用成本

**前置依赖**：`comment.cid`（否则无法回写结果到具体评论）

#### 3.1.2 情感分析增强

| 改进 | 说明 | 优先级 |
|------|------|--------|
| 启用现有 529 词词典 | SnowNLP 分数落在 [0.4,0.6] 灰区时用词典二次判定 | P1 |
| 阈值可配置 | 从 `application.yml` 读，不用硬编码 | P1 |
| 建立标注集 | 人工标注 200~500 条（覆盖短评论/emoji/反讽/方言） | P1 |
| 准确率回归测试 | 标注集作为 CI 断言（如准确率 ≥ 80%） | P1 |

### 3.2 视频级（当前主战场）

#### 3.2.1 多维度结构化报告（替换现有 Markdown 报告）

**目标**：保留现有 Markdown 报告（给人看），**新增**结构化 JSON（给程序用）。

```json
{
  "video_id": "7703721523349239951",
  "summary": {
    "total_comments": 320,
    "sentiment_distribution": {"positive": 0.42, "neutral": 0.31, "negative": 0.27},
    "hot_regions": [{"region": "辽宁", "ratio": 0.55}]
  },
  "user_needs": [
    {"need": "配送时效", "frequency": 89, "priority": "high",
     "evidence": ["评论ID:xxx", "评论ID:yyy"], "user_quote": "快递三天没动静"}
  ],
  "pain_points": [
    {"pain": "包装破损", "frequency": 45, "severity": "high",
     "affected_users": 45, "quotes": [...]}
  ],
  "purchase_intent": {
    "high": 23, "medium": 45, "low": 78,
    "intensity_score": 0.41,
    "hot_categories": ["入门款", "礼盒装"]
  },
  "product_pros": [{"aspect": "性价比", "mentions": 67, "representative_quotes": [...]}],
  "product_cons": [{"aspect": "色差", "mentions": 23, "severity": "medium", ...}],
  "topics": [{"topic": "物流", "heat": 0.72, "sentiment": -0.31, "trend": "上升"}],
  "risks": [{"type": "合规", "desc": "...", "level": "high"}],
  "suggestions": [{"action": "...", "basis": "..."}]
}
```

**实现要点**：

| 项 | 方案 |
|----|------|
| 输入 | 分批传入评论原文（每批 50~100 条），而非仅统计特征 |
| 聚合 | 多批结果由 Java 侧或 Flask 侧做频次聚合与去重 |
| 证据溯源 | 每个结论携带 `evidence`（评论ID数组），保证可核查 |
| 双输出 | 同时保留现有 Markdown（`/analyze_topic`）与新增 JSON（`/analyze_insights`） |
| 缓存 | 视频级结果持久化到新表 `video_insight`，不再只靠 30 分钟内存缓存 |

**成本估算**：
- 320 条评论 ÷ 80 条/批 = 4 次调用
- 每批约 5000~8000 tokens 输入
- 单视频单次全量分析 ≈ 2~3 万 tokens ≈ 0.1~0.2 元（按 DeepSeek 定价估算，**需实际核对当前价格**）

**前置依赖**：`comment.cid`（证据溯源）、`video` 表（视频元数据）

#### 3.2.2 增量分析

同一视频二次分析时，只处理新增评论（基于 `cid` 与 `video_insight` 中已处理的 cid 集合），
结果合并到已有结论。**成本可降至增量的 1/N**。

### 3.3 关键词级（横向对比）

#### 3.3.1 关键词 → 视频发现与分析

**前置**：`keyword` 表、`video` 表、搜索功能（当前 D 级缺失）

```
关键词表 → 定时/手动触发发现 → video 表（去重台账）
        → 采集任务 → comment 表
        → 视频级分析 → video_insight 表
        → 关键词级聚合（对比各视频的需求/痛点/意图分布）
```

关键词级聚合示例：

```json
{
  "keyword": "空气炸锅",
  "video_count": 24,
  "total_comments": 5800,
  "aggregate_pain_points": [
    {"pain": "涂层脱落", "video_count": 8, "total_mentions": 156, "severity": "high"}
  ],
  "purchase_intent_trend": [{"date": "2026-10", "score": 0.38}, ...],
  "competitor_landscape": [
    {"product": "品牌A", "video_count": 9, "sentiment": 0.12, "top_praise": ["容量大"], "top_complaint": ["噪音大"]}
  ]
}
```

#### 3.3.2 竞品对比分析

**前置**：视频元数据中含品牌/产品标识，或通过 LLM 从评论中抽取 `mentioned_products`。

```
评论级抽取 mentioned_products → 聚合到 product 表
                              → 按产品聚合痛点/优点
                              → 生成竞品对比矩阵
```

### 3.4 行业级（趋势与热点）

| 能力 | 依赖 | 说明 |
|------|------|------|
| 行业热点识别 | 定时采集 + 时间序列 | 按关键词/主题统计评论热度随时间变化 |
| 趋势追踪 | `video_insight` + `video` 的 `discovered_at` | 同一主题在不同时间的表现对比 |
| 需求演化 | 历史 `video_insight` 快照 | 用户需求随时间的新增/消失 |
| 竞品格局 | 产品级聚合 | 品类内的产品口碑分布 |

**这层必须有定时采集能力**（当前无 APScheduler/Celery）。
建议：Spring Boot `@Scheduled` + 数据库任务表轮询，不引入额外中间件。

## 4. RAG 的适用性评估（任务卡提及）

### 4.1 是否需要 RAG

| 场景 | 需要 RAG？ | 理由 |
|------|-----------|------|
| 单视频需求提取 | ❌ | 上下文可全部放入 Prompt |
| 关键词级对比 | ❌ | 聚合后传结构化摘要即可 |
| 行业级报告 | ⚠️ 可能有价值 | 需检索历史分析结论做对比 |
| 报告引用溯源 | ⚠️ | 若要"引用历史报告"，需检索 |

**结论：当前阶段不需要引入 RAG。**
在评论量级（万级）下，直接把相关评论放入 Prompt 成本可控且效果更准。
RAG 的价值在语料规模远超上下文窗口时才显现。

**未来触发条件**：
- 单次分析需处理 > 50 万条评论
- 需要跨月/跨年对比历史分析结论

### 4.2 主题聚类

| 方案 | 复杂度 | 效果 | 建议 |
|------|--------|------|------|
| LLM 直接聚类 | 低 | 主观，每次结果可能不同 | ✅ 先用这个 |
| jieba + TF-IDF + KMeans | 中 | 可复现，但需调参 | P2 备选 |
| 嵌入向量 + HDBSCAN | 高 | 最佳 | 需引入向量模型 |
| LLM 抽取主题标签 + 频次聚合 | 低 | **可复现且贴近业务** | ✅ **推荐** |

**推荐方案**：LLM 抽取标准化主题标签（如"物流时效""包装质量"），Java/Python 侧按标签频次聚合。
理由：主题标签可直接用于跨视频聚合（关键词级、行业级分析），而 KMeans 的簇编号无业务含义。

## 5. 技术选型建议（不引入新技术的原则）

| 需求 | 建议方案 | 是否引入新技术 |
|------|---------|--------------|
| 批量 LLM 调用 | 复用现有 Flask 服务，新增端点 | ❌ 复用 |
| 结构化输出 | OpenAI SDK 的 `response_format=json_object` | ❌ 复用 |
| 调用限流 | `threading.Semaphore` | ❌ 标准库 |
| 结果缓存 | MySQL 新表 + 现有 `MemoryCache` | ❌ 复用 |
| 定时任务 | Spring Boot `@Scheduled` | ❌ 复用 |
| 任务队列 | 数据库任务表 + 轮询调度器 | ❌ 不引入 MQ |
| 嵌入/向量检索 | **暂不做**（RAG 非必需） | ✅ 暂不引入 |

**唯一可能引入的新依赖**：若要做高质量情感分析，可考虑中文情感专用模型（如 `RoBERTa-wwm`），
但需要 GPU 或量化部署，**当前阶段建议先优化现有方案**。

## 6. AI 能力路线图

```
阶段 A（现有）：统计特征 → LLM → Markdown 统计报告
   │  已上线
   ▼
阶段 B（P1）：评论原文 → LLM → 结构化 JSON（含需求/痛点/意向）
   │  需: comment.cid + 新增 Flask 端点 + 成本控制
   ▼
阶段 C（P1）：视频级 JSON 聚合 → 关键词级对比
   │  需: video 表 + keyword 表 + 搜索能力
   ▼
阶段 D（P2）：定时采集 + 时间序列 → 行业热点与趋势
   │  需: @Scheduled + 任务调度 + 历史快照
   ▼
阶段 E（P2）：产品实体抽取 → 竞品对比矩阵
   │  需: mentioned_products 抽取 + 产品表
```

**阶段 B 是分水岭**：不做 B，C/D/E 都无从谈起（因为需要结构化的中间产物）。

## 7. 成本控制设计

| 手段 | 效果 | 实现 |
|------|------|------|
| 分层分析 | SnowNLP 预筛，只对模糊样本调 LLM | 省 60~70% |
| 增量分析 | 只分析新增评论 | 二次分析成本降至 1/N |
| 结果持久化 | 报告存 `video_insight` 表，不重复调用 | 重启后免付费 |
| Prompt 精简 | 用结构化摘要替代原文（视频级统计） | 省 80%（但损失细节） |
| Token 上限 | 评论级 300、洞察级 4000 | 控制单次成本 |
| 预算护栏 | 每日 token 计数器，超限降级 | 防止意外 |

## 8. 关键前置依赖（必须先做）

| 依赖 | 阻塞的能力 | 优先级 |
|------|-----------|--------|
| `comment.cid` | 评论级结构化分析（证据溯源、增量） | **P0** |
| `video` 表 | 视频级元数据、关键词级分析 | P1 |
| `collect_task` 表 | 定时采集、行业级分析 | P0 |
| 关键词搜索功能 | 关键词级、行业级 | P1 |
| 结构化输出端点 | 全部新能力 | P1 |

**结论**：AI 能力升级的瓶颈不在模型，而在**数据底座**（cid、video 表、任务表）。
建议先补数据底座，再上 AI 能力。
