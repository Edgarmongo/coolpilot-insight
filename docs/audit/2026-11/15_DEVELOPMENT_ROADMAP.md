# 15 · DEVELOPMENT_ROADMAP

> 开发路线图（基于本次审计结论）
> 原则：每项任务独立可交付；不把未验证的假设写成确定需求

---

## 总体路线

```
P0 基础可靠性（数据不丢、任务可控）
   ↓
P1 核心 AI 能力（从"报告生成"到"需求洞察"）
   ↓
P2 业务产品能力（规模化、自动化、对比分析）
   ↓
P3 平台扩展能力（多租户、多平台、Agent）
```

**依赖链说明**：

```
P0-1 任务表 ──┬─→ P0-2 任务调度器 ──→ P1-3 多视频批量
               ├─→ P2-1 定时采集
               └─→ P2-3 竞品分析
P0-3 cid 唯一键 ──┬─→ P1-1 评论级结构化分析
                  ├─→ P1-2 视频级洞察
                  └─→ P0-4 增量采集
P0-5 video 表 ──┬─→ P1-4 多视频联合分析
                └─→ P2-2 行业热点
P1-1/2 ──→ P2-4 报告中心
```

## P0：基础可靠性

### P0-1 · 采集任务表与状态持久化

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **现状** | 状态仅存 `ConcurrentHashMap`（`CollectServiceImpl:20`），重启即丢；无历史可查 |
| **问题** | 任务状态不可追溯；无法统计成功率；无法支撑调度器 |
| **涉及文件** | 新建 `dy-backend/.../entity/CollectTask.java`、`mapper/CollectTaskMapper.java`、`service/CollectTaskService.java`；改 `CollectServiceImpl`、`CollectController` |
| **涉及表** | 新建 `collect_task`（DDL 见 04 号文档 5.1） |
| **技术方案** | 任务创建时落库；状态流转更新表；`MemoryCache` 降级为纯内存加速层，DB 为准 |
| **前置依赖** | 无 |
| **验收标准** | ① 创建任务后重启容器，`GET /api/collect/tasks` 仍能查到任务及状态 ② 任务列表含 video_id/status/开始时间/完成时间/失败原因 ③ 可按状态与用户筛选 |
| **风险** | 低。纯新增表与新接口，不改动现有行为 |
| **工作量** | **2~3 人日** |

### P0-2 · 采集数据流式落盘（消除中断全丢）

| 项 | 内容 |
|----|------|
| **优先级** | **P0（最高性价比）** |
| **现状** | `douyin_comment.py` 内存累积 → 循环结束后一次性写 CSV |
| **问题** | 实测中断（kill -9）后已采 10 条全部丢失 |
| **涉及文件** | `Py_Data/douyin_comment.py` |
| **涉及表** | 无 |
| **技术方案** | ① 采集循环内每页 `open(csv_path, 'a')` 追加写入 ② 写入前先落表头（用 `os.path.exists` 判断）③ 断点续采：把已写行数记录到 `.progress` 文件，重跑时跳过 |
| **前置依赖** | 无 |
| **验收标准** | ① 采集中 kill -9，已采评论仍在 CSV 中（≥1 页）② 重跑时不产生重复行（按 cid 或内容去重）③ 中断后重跑可继续 |
| **风险** | 低。改动局限于文件写入逻辑 |
| **工作量** | **0.5~1 人日** |

> **建议第一个做**——改动最小、收益最直接。

### P0-3 · 评论唯一 ID 与唯一索引

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **现状** | `comment` 表无 `cid`；去重靠 `(昵称, 内容)` 内容比对 |
| **问题** | ① 无法识别评论更新 ② 无法精确去重 ③ 「先查后插」非原子，并发清洗有竞态 ④ 无法做增量采集 |
| **涉及文件** | `Py_Data/douyin_comment.py`（采集 `cid`）、`Py_Data/clean/clean_main.py`（入库）、`dy-backend/.../entity/Comment.java` |
| **涉及表** | `comment` 加 `cid VARCHAR(32)` + `UNIQUE KEY uk_cid` |
| **技术方案** | ① 采集时读接口的 `cid` 字段（已验证接口返回该字段）② 入库改 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE` ③ 去重键升级为 `cid`（缺失时回退 `(昵称,内容)`） |
| **前置依赖** | 无（但需先确认抖音 `cid` 稳定唯一——**建议在开发前用真实数据抽验**） |
| **验收标准** | ① 采集的 CSV 含 `cid` 列且非空率 > 99% ② 并发清洗同一视频不产生重复行 ③ 唯一索引存在 ④ 重复采集时 `INSERT IGNORE` 生效 |
| **风险** | 中。需 DB 迁移（`ALTER TABLE`），已有数据 `cid` 为 NULL 不影响唯一索引（MySQL 允许多个 NULL） |
| **工作量** | **1~2 人日** |

### P0-4 · 采集任务去重与并发管控

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **现状** | `startCollect` 无状态检查，裸线程无限创建 |
| **问题** | 实测 3 次并发提交同一视频 → 2 个任务失败（Chrome profile 争抢） |
| **涉及文件** | `dy-backend/.../service/impl/CollectServiceImpl.java`、`CollectController.java` |
| **涉及表** | `collect_task`（P0-1） |
| **技术方案** | ① 提交前检查同 video_id 是否已有 PENDING/RUNNING 任务 → 返回"任务进行中" ② 全局 `ThreadPoolExecutor(core=1, max=2)` ③ 每任务独立 profile 目录 `chrome-data/task-{taskId}`（若需真正并发） |
| **前置依赖** | P0-1（任务表） |
| **验收标准** | ① 重复提交同一视频返回明确提示而非启动第二个任务 ② 并发提交不同视频不出现 profile 冲突 ③ 线程数有上限 |
| **风险** | 低 |
| **工作量** | **1~2 人日** |

## P1：核心 AI 能力

### P1-1 · 评论级结构化分析

| 项 | 内容 |
|----|------|
| **优先级** | P1（**AI 升级的分水岭**） |
| **现状** | 仅三分类情感（SnowNLP） |
| **问题** | 无需求/痛点/意向/主题抽取能力 |
| **涉及文件** | `Py_Data/clean/wordcloud_service.py`（新增端点）、`dy-backend/.../AnalysisServiceImpl`（新增编排） |
| **涉及表** | `comment` 加 `analysis_json MEDIUMTEXT`（结构化结果） |
| **技术方案** | ① 新增 `/analyze_comments`：批量传评论原文 → LLM → **强制 JSON 输出**（`response_format={"type":"json_object"}`）② 输出含 sentiment/intent/topics/pain_points/purchase_intent/user_need ③ 失败重试 1 次 + 字段校验 ④ SnowNLP 预筛降低调用量 |
| **前置依赖** | P0-3（cid 溯源） |
| **验收标准** | ① 单条评论可输出结构化标签 ② JSON 解析成功率 ≥ 95% ③ 结果可按主题/意向聚合查询 ④ 有 Token 消耗统计 |
| **风险** | 中。成本上升（估算 150~300 tokens/条，**需按实际定价核算**） |
| **工作量** | **4~6 人日** |

### P1-3 · 多视频批量采集

| 项 | 内容 |
|----|------|
| **优先级** | P1 |
| **现状** | `videoId` 为 String，接口不支持数组（实测 400） |
| **问题** | 无法一次任务处理多个视频；README 描述与实现不符 |
| **涉及文件** | `CollectRequest.java`（改 List）、`CollectController.java`、`CollectServiceImpl.java`、前端 `CollectView.vue` |
| **涉及表** | `collect_task`（video_ids JSON） |
| **技术方案** | ① DTO 接受 `List<String> videoIds`（向后兼容单值）② 任务内串行执行各视频（**先串行，不并发**）③ 单视频失败不影响其余，记为 PARTIAL_SUCCESS ④ 前端支持多行输入 |
| **前置依赖** | P0-1、P0-4 |
| **验收标准** | ① 一次提交 N 个视频可完成采集 ② 部分失败时状态为 PARTIAL_SUCCESS 且列出失败项 ③ 单视频失败不中断整批 |
| **风险** | 低 |
| **工作量** | **3~4 人日** |

### P1-5 · AI 成本与并发管控

| 项 | 内容 |
|----|------|

| **风险** | 低 |
| **工作量** | **2 人日** |
