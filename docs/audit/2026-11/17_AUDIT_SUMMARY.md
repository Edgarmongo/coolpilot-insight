## 0. 审计结论一句话

**系统是一个「可运行的单视频采集 → 清洗入库 → 单视频统计报告」闭环工具，
但距离任务卡描述的「关键词发现 → 多视频批量 → AI 需求洞察平台」存在结构性差距；
且采集链路的可靠性（并发踩踏、中断丢数据）与数据底座（无 cid、无 video 表、无任务表）
是当前最紧迫的短板。**

## 4. 采集能力评价（任务卡明确要求回答）

| 问题 | 回答 |
|------|------|
| **关键词搜索是否可靠** | ❌ **该能力不存在**。用户必须人工到抖音搜索并复制链接 |
| **视频发现是否完整** | ❌ **不完整**。仅支持从链接提取单个 ID，5 种形式兼容（纯数字 / /video/ /note/ /share/video/ ?modal_id=） |
| **多视频采集如何执行** | ❌ **无法执行**。接口层 `videoId` 是 String，实测数组 400 |
| **是否真正并发** | ❌ **既不支持多视频，也无安全并发**。裸线程 + 共享 Chrome profile，实测 3 并发仅 1 成功 |
| **评论分页是否完整** | ⚠️ **不完整**。靠滚动触发 + 被动捕获，**未使用 cursor**；匿名态约 3 页 15 条后 `has_more=0` |
| **是否存在重复数据** | ✅ **不存在**。批内 + 跨批次双层去重，实测重复采集后「跳过重复 13 条」，库中 14 条无重复 |
| **是否支持增量采集** | ❌ **不支持**。每次全量重拉，靠入库层去重兜底；因抖音按热度排序，**新增评论实际可能漏采** |
| **是否支持失败恢复** | ❌ **不支持**。中断后已采数据全丢，无游标、无重试、无断点续采 |

## 5. AI 能力评价（任务卡明确要求回答）

| 问题 | 回答 |
|------|------|
| **当前情感分析实现方式** | SnowNLP 贝叶斯分类器，阈值硬编码 0.4/0.6。**已有的 529 词情感词典完全未被引用**（死代码），README 描述与实现不符 |
| **当前核心话题分析实现方式** | Java 侧算 5 维度聚合统计 → Flask 拼 Prompt → DeepSeek 生成 Markdown。**LLM 只看统计特征，从不看评论原文** |
| **DeepSeek 调用链** | `GET /api/analysis/topic` → `computeTopicDims` → HTTP POST `http://flask:5000/analyze_topic` → OpenAI SDK（base_url=api.deepseek.com）→ deepseek-chat（temp 0.7, max_tokens 2000, timeout 30s）→ Markdown → 缓存 30 分钟。**三级降级：正常 → 统计报告 → 空** |
| **当前 AI 分析的限制** | ① 结构上无法做需求/痛点/意向提取（无原文）② 输出是 Markdown，不可程序消费 ③ 无 Token 统计、无预算、无并发限制 ④ 无响应持久化（重启重复付费）⑤ Java readTimeout 与 Flask timeout 相同无余量（可能扣费但丢结果）⑥ 单视频视角，无法跨视频聚合 |
| **下一阶段最值得开发的 AI 能力** | **评论级结构化分析**（T-09）——它是分水岭。做到"LLM 看到原文 + 强制 JSON 输出"，需求/痛点/意向全部解锁，且是视频级洞察、关键词级聚合、行业级趋势的共同前置 |

## 8. 给决策者的三句话

1. **可以跑的，但规模化的地基是空的**：现在能采一个视频、出一份报告；要支撑"批量发现 → 稳定采集 → 需求洞察"，缺的是 `cid`、`video` 表、`collect_task` 表这三块地基。

2. **最紧急的不是加功能，是止漏**：并发踩踏和中断丢数据两个 P0 问题，会让任何批量采集的尝试都不可靠。建议先做 T-01（1 天内可完成，消除中断丢数据）。

3. **AI 的瓶颈在数据不在模型**：DeepSeek 接入本身是完整可用的，但 LLM 只能看到聚合统计、看不到评论原文——这是需求分析能力的**结构性天花板**。改成"传原文 + 强制 JSON 输出"，是 AI 能力跃迁的唯一前提。
