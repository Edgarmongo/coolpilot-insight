# C-03.1 · 三个缺陷的影响面审计与修复设计

日期：2026-11-16 03:32　**仅设计，未改代码**

## 缺陷 1：Item 与 Run 的关联语义

### 现状

```
submit()  → Task + Item(PENDING)        ← Item 创建时 Run 还不存在
trigger() → Run                          ← Run 后建，无人回填 Item
runTask() → 遍历该 Task 的全部 Item，跳过非 PENDING/RETRY_WAIT
```

`collection_task_item` 是**内容对象与任务的关系**（一个任务下某视频的采集状态），
不是"某次运行的执行记录"。把它当成 Run 的从属会破坏语义。

### 四个问题的结论

| 问题 | 结论 |
|---|---|
| 一个 Task 多个 Run 时，历史 Item 如何处理 | **不处理**。Item 属于 Task，Run 只是"处理过它" |
| 新 Run 是否只关联本次待执行的 Item | **是**。只有 `PENDING`/`RETRY_WAIT` 的 Item 参与执行并回填 `run_id` |
| 已 SUCCESS 的 Item 是否被新 Run 重新关联 | **否**。不参与执行的 Item 保持原 `run_id` 不变 |
| 失败 Item 重试时归属如何表达 | 重试创建新 Run，该 Item 的 `run_id` **更新为新 Run**（表示最近一次处理者），历史归属靠 `collection_task_log.run_id` 追溯 |

### 建议语义（明确写进代码注释）

> `collection_task_item.run_id` = **最近一次处理该 Item 的 Run**，不是所有权。
> 未被任何 Run 处理过则为 NULL（历史数据即如此）。

### 回填时机

**在 dispatch 领取 Run 成功之后、执行之前**，由 `RunApplicationService` 统一回填：

```sql
UPDATE collection_task_item SET run_id = :runId
 WHERE task_id = :taskId AND status IN ('PENDING','RETRY_WAIT') AND run_id IS NULL;
```

只回填 `run_id IS NULL` 的，避免覆盖历史归属。放在应用服务，不放 Controller/Mapper。

### 为什么不建 item_run 关联表

完整历史归属需要多对多表，属 Schema 变更。当前用 `collection_task_log`（已加 `run_id`）
承载"哪个 Run 处理过什么"足够追溯。**若后续需要按 Run 反查全部 Item，需单独提评审。**

## 缺陷 2：`maxComments` 未生效

### 根因（已定位到行）

`collection-service/app/adapters/douyin/comment.py`：

```python
MAX_COMMENTS = int(sys.argv[2]) ...     # 参数确实传进来了
while data_count < MAX_COMMENTS:        # 循环条件正确
    rows = 取当前页                        # 一页 19 条
    if data_count + len(rows) >= MAX_COMMENTS:
        append_rows(rows)               # ← 整页写入，未截断
```

**不是没传参，也不是没判断，而是"整页追加"突破了上限。**

### 修复（Python 侧，唯一有效位置）

```python
remaining = MAX_COMMENTS - data_count
if remaining <= 0:
    break
rows = rows[:remaining]                 # 关键：截断最后一页
```

**为什么不能在 Java 入库时截断**：Python 会继续滚动抓取，产生多余请求，
在限流场景下直接触发风控。

### 三个数量必须分开统计

| 字段 | 含义 | 现状 |
|---|---|---|
| `fetched_count` | 平台返回的原始条数 | 无（Java 未记录） |
| `processed_count` | 截断后实际处理的条数 | 无 |
| `inserted_count` / `duplicate_count` | 入库与去重 | 仅 item.collected_count 含糊记录 |

建议 Execution 落地时同时记录三者，避免"返回 19、入库 0"这类数字无法自证。

## 缺陷 3：Execution 生命周期

### Python 的实际执行粒度

一次 `invokeCollector()` = 一个视频 = 一次进程调用 = 一个 Execution。
所以 **Execution 粒度 = Item 粒度**（1:1），不是"一个 Run 一个 Execution"。

### 设计

| 字段 | 取值来源 |
|---|---|
| `run_id` | 领取时已知 |
| `source_id` | Task.source_id（回填后存在） |
| `auth_mode` | 本次为 `PUBLIC`；登录态为 `AUTHENTICATED` |
| `account_id` | PUBLIC 必须 NULL（CHECK 约束已保证） |
| `capability` | `FETCH_COMMENTS` |
| `status` | PENDING → RUNNING → SUCCEEDED/FAILED/CANCELLED/SKIPPED |
| `failure_type` | 七类枚举，由 error_code 映射 |
| 统计 | request/fetched/inserted/duplicate/failed |

### 写入时机

- **创建**：`runItem()` 开始时插入 PENDING，随即置 RUNNING
- **更新**：采集返回后写统计与终态
- **禁止**：一次 Run 无实际采集却创建 Execution（例如所有 Item 都跳过）

## 修复顺序与验收

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | `run_id` 回填（应用服务统一） | 新 Run 执行后 Item.run_id 非空；历史 SUCCESS Item 的 run_id 不变 |
| 2 | `maxComments` 截断（Python） | 请求 5 → Python 处理 ≤5，日志显示截断 |
| 3 | Execution 落地 | 每次实际采集有 1 条 col_execution，统计三数分明 |
| 4 | 新视频验证 | 至少 1 条新增；CID 去重；checkpoint 一致 |

## 待确认

1. `Item.run_id` 采用"最近一次处理者"语义是否可接受（替代方案：建 item_run 表，需 Schema 评审）
2. `maxComments` 修复是否允许改 Python adapter（C-03 禁令为"不改变平台采集 Adapter 行为"，
   但截断属参数约束而非采集行为，需你确认边界）
3. Execution 与 Item 1:1 是否符合预期
