## 1. 背景

当前系统**没有 Redis**（无依赖、无服务、无客户端）。已有缓存全部是进程内的：

- `MemoryCache`：3 个分析结果 Key，TTL 5 分钟，**前缀失效存在缺陷**；
- `SnapshotCache`：能力快照，TTL 60 秒，**参与执行准入判定**；
- `TokenStore`：登录 token，进程内 Map。

三个事实决定了这个决策的性质：

1. **没有性能证据**：无 QPS、无慢查询、无命中率数据 → 不能以"性能问题"立项；
2. **单实例运行**：backend 单副本、collection 硬约束单副本 → 跨进程共享暂非刚需；
3. **已有两处质量缺陷**（失效不生效、重启掉登录）→ 引入缓存层应先修契约，而不是先搬实现。

---

## 2. 决策

**引入单机 Redis 7，仅作为"查询结果缓存"使用；不承担任何业务事实、状态机或认证存储职责。**

### 2.1 允许

- 查询结果缓存（列表、详情、聚合统计）
- 热点数据缓存
- 统计结果缓存
- **已发布快照的原文副本**（不是准入判定依据）

### 2.2 不允许

- 业务数据持久化（唯一事实仍在 MySQL）
- 任务状态、任务租约、Run 状态（`col_run` / `lease_until` 不变）
- 替代数据库事务
- 存储密码、API Key 明文、平台 Cookie、任意凭证明文
- **缓存权限/授权判定结果**（授权变更无法即时失效，易越权）
- 作为 Python 与 Java 之间的数据交换通道（见 §5 约束二）
- 承担分布式任务协调（见 §5 约束三）

### 2.3 本期明确"不进 Redis"的两个对象

| 对象 | 原因 |
|---|---|
| `SnapshotCache`（能力快照） | 它的状态直接决定采集能否执行；网络抖动会被放大成准入判定抖动；若在 Redis 故障时回退进程内旧副本，会出现"用陈旧快照放行执行"的安全问题 |
| `TokenStore`（登录 token） | 属认证链路。迁入后 Redis 从"可选加速件"变成"认证强依赖"，可用性要求完全不同 → 单列为候选决策 D-1（见 `CACHE-CANDIDATE-ANALYSIS.md` §3） |

## 3. 与 MySQL 的关系：Cache-Aside

### 3.1 读

```
请求 → 查 Redis
        ├── 命中 → 返回
        └── 未命中 → 查 MySQL → 写 Redis(TTL) → 返回
```

### 3.2 写（关键）

```
1. 更新 MySQL
2. 事务提交成功
3. 删除相关 Redis Key
4. 下次读取时重新加载
```

**失效必须在事务提交之后**。事务内删除会留下"回滚了但缓存已删/已脏"的窗口。
对一致性要求高的场景（如能力 Desired 变更），采用 **删除** 而不是 **更新** 缓存
（避免并发写覆盖），必要时引入 Outbox/可靠失效，而不是仅依赖一次 delete。

### 3.3 一致性等级（明确写死，避免过度承诺）

| 数据 | 一致性要求 | 手段 |
|---|---|---|
| 数据源/能力配置 | 秒级最终一致 | 写入后删 Key + TTL 兜底 |
| 统计聚合 | 分钟级最终一致 | 纯 TTL，不做主动失效 |
| 分析结果（词云/主题） | 分钟级最终一致 | TTL + 修复后的前缀失效 |
| 任务状态 | **强一致** | 不进缓存 |

---

## 4. 故障原则（Redis 不能成为单点）

| 场景 | 期望行为 |
|---|---|
| Redis 不可达（连接失败/超时） | 记录 WARN，**回源 MySQL**，请求正常返回 |
| Redis 读超时 | 同上（超时阈值 < 业务超时，快速失败） |
| Redis 写失败 | 记录日志，不影响业务返回 |
| Redis 重启 | 缓存自然重建，无业务影响 |
| Redis 数据被清空 | 无业务影响（缓存可重建） |
| Redis 认证失败 | 视为不可用，**不得重试风暴**（退避+告警） |

**硬性要求**：Redis 全面不可用时，`/api/**` 的核心读写必须仍然可用。
这一条是 Phase 7 故障演练的判据，不是口号。

---

## 5. 三条架构约束（写入架构文档，长期有效）

### 约束一：缓存不能成为业务事实来源

任何业务数据都必须能**从 MySQL 或合法原始数据重新构建**。
"缓存里有、库里没有"视为缺陷，不是特性。

### 约束二：Redis 不承担 Python ↔ Java 的数据交换

首期 Redis **仅由 Java 业务服务使用**。
Python（采集 / 清洗 / AI）仍通过既有接口提交结果，不读写 Redis。
将来若确需 Python 访问，必须单独做安全与职责评审（凭证分发、键空间隔离、误删风险）。

### 约束三：Redis 不承担分布式任务协调

任务状态与租约继续由 MySQL 行状态 + `lease_until` 承担。
不得因为"已经有 Redis 了"就把任务锁、调度、状态迁移过去。

---

## 6. 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 继续用 `MemoryCache`，不引入 Redis | 无法跨实例共享；重启即失效；且现有实现缺少容量上限与统计 |
| 用 Caffeine 等本地缓存增强 | 同样不跨进程；适合替代 `MemoryCache` 的实现质量，但不解决多实例问题 |
| 用 MySQL 表当缓存 | 增加写压力与锁竞争，TTL 清理需要额外机制，收益为负 |
| Redis Cluster / 哨兵 | 单实例单机足够；集群带来运维复杂度与一致性面，与当前规模不匹配 |
| Redis 存任务队列 | 与现有 `JobQueue` + DB 租约冲突，会形成两套事实 |

---

## 7. 后果

**正面**

- 统一缓存 Key/TTL/序列化/失效契约，消除三处各写一套的现状；
- 为将来 backend 多实例提供共享缓存基础；
- 修掉"前缀失效不生效"这类既有缺陷（迁移时强制重写失效逻辑）。

**负面 / 成本**

- 新增一个有状态服务与一套运维面（内存、淘汰、监控、ACL）；
- 引入"缓存与库不一致"这一类新故障模式，需要 TTL 与失效纪律；
- 目前**没有证据表明性能会显著改善**——收益是结构性的，不是可量化的。

**不做的事**

- 不改动 SOURCE-04 契约、任务状态机、采集执行链路；
- 不因此改变 collection 单副本约束；
- 不把 Redis 当作"必须有"的中间件塞进所有模块。

---

## 8. 生效条件

本 ADR 转为 Accepted 需同时满足：

1. Phase 0 三份审计材料评审通过；
2. 本 ADR 的三条约束被写入 `PRODUCT-ARCHITECTURE.md`（架构演进约束一节）；
3. 监控埋点方案（命中率、延迟、淘汰数）与缓存层同批设计；
4. 明确"Redis 不可用"的验收判据（Phase 7 故障演练清单）。
