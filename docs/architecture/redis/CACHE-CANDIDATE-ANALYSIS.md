# 缓存候选分析（CACHE-CANDIDATE-ANALYSIS）

> 任务：CP-REDIS-01-01（只读）
> 基线：`96a57dd`
> 判断依据：读取路径（`CACHE-USAGE-INVENTORY.md` §6）+ 数据变更频率 + 一致性的代价

---

## 0. 先给结论

**值得进 Redis 的候选只有 4 类，且都不是"救火"，是"打底"。**

当前没有任何观测数据能证明 MySQL 有压力（无慢查询记录、无 QPS 统计）。
因此本项目的定位应当是：
**统一缓存契约 + 为多实例做准备 + 把现有 3 个 Key 的缺陷修正**，
而不是"性能优化"。

---

## 1. 候选清单

| # | 数据类型 | 现状 | 建议 | 初始 TTL | 优先级 | 理由 |
|---|---|---|---|---|---|---|
| R-01 | 数据源配置查询（`/api/v1/source/sources`） | 每次查 DB + 快照 | **进 Redis** | 5 min（±30s 抖动） | **高** | 低频变更、高频读取；`Desired` 改动可显式失效 |
| R-02 | 统计聚合结果（overview 概览、TopN、趋势） | 每次实时聚合多表 | **进 Redis** | 5 min | **高** | 计算成本高于单次查询；可接受分钟级陈旧 |
| R-03 | 分析结果（词云 / 桑基图 / 主题） | 已在 `MemoryCache` | **迁移到 Redis** | 5 min | **高** | 现成对象，迁移即验证缓存层；顺带修失效 bug |
| R-04 | 内容列表分页（评论列表） | 每次实时查询 | **进 Redis**（条件式） | 1 min | 中 | 高频但参数组合多；键空间膨胀风险需压测 |
| R-05 | 内容详情 | 每次查 DB | 暂缓 | 3 min（备选） | 低 | 单条查询已很快，缓存收益有限 |
| R-06 | 能力快照（Observed） | `SnapshotCache` 60s 进程内 | **保留进程内**（不进 Redis 首期） | — | — | 参与准入判定，网络抖动会放大为判定抖动 |
| R-07 | 登录 token（`TokenStore`） | 进程内 Map | **单列决策 D-1** | 与 JWT 一致 | 待定 | 收益最大（重启不掉线、多实例一致），但属认证链路 |
| R-08 | 任务状态 / 租约 | MySQL 权威 | **禁止缓存** | — | — | 缓存会破坏状态机与租约语义 |
| R-09 | 凭证 / API Key / Cookie | 未入库明文 | **禁止进缓存** | — | — | 敏感信息，见安全分级 L3 |
| R-10 | 原始评论与视频正文 | 存 MySQL | **首期不纳入** | — | — | 体积与个人信息评估未完成 |
| R-11 | 权限判定结果 | 每次查库 | **禁止缓存** | — | — | 缓存的权限结果无法随授权变更即时失效，易越权 |

## 2. 三张"不做"清单（比"做"更重要）

### 2.1 禁止进 Redis

- 任务状态、任务租约、Run 记录（MySQL 是唯一事实）；
- 权限/授权判定结果（`GovernanceService` 的结论）；
- 凭证、API Key、Cookie、任意登录凭据；
- 任何"删掉了就重建不出来"的数据。

### 2.2 保留进程内

- `SnapshotCache`（准入语义，见 `CACHE-USAGE-INVENTORY.md` §3）；
- 单次请求内的临时结构（无跨请求价值）；
- `LayeredHealthService` 的实时探测（缓存它会掩盖故障）。

### 2.3 首期不碰

- 评论正文与视频正文（体积 + 个人信息分级未定）；
- 报告正文（生成成本高但频率低，缓存收益不明确）。

## 3. 关键决策 D-1：登录 token 要不要进 Redis

| 维度 | 留在进程内（现状） | 迁到 Redis |
|---|---|---|
| 重启后登录态 | **全部失效**，用户需重新登录 | 保留 |
| 多实例登出/封禁 | 只对当前实例生效（**安全漏洞面**） | 全局一致 |
| Redis 故障时 | — | **登录/鉴权可能整体不可用**（必须设计降级） |
| 实现成本 | 0 | 需改造 `JwtInterceptor` + 降级策略 + 迁移窗口 |

**为什么单列**：它不是"缓存"，是"会话存储"。放进去以后，
**Redis 从"可选加速件"变成"认证链路的强依赖"**，可用性要求完全不同。

**建议**：首期**不做**。等 Redis 稳定运行一个迭代、且确有第二个 backend 实例的需求时，
再作为独立任务（CP-REDIS-02）评审，并明确"Redis 不可用时是否允许降级为无状态 JWT 校验"。

## 4. 候选的收益估算（诚实版）

| 候选 | 预期收益 | 依据 |
|---|---|---|
| R-01 数据源列表 | 中等 | 每次请求要查 `ds_source` + 快照 + 推导 Effective；页面常开时轮询明显 |
| R-02 概览聚合 | **较高** | 多表 count/聚合，是最重的一类查询 |
| R-03 分析结果 | 低（迁移收益） | 本来就有缓存，只是搬到 Redis；主要收益是修 bug + 统一契约 |
| R-04 评论列表 | 待验证 | 键空间 = 视频 × 页码 × 筛选条件，可能膨胀 |

**必须承认**：在没有 QPS/慢查询数据前，以上都是**结构性推断**，不是实测结论。
Phase 7 的灰度必须带"迁移前后对比"，否则无法验证收益。

---

## 5. 迁移顺序建议

按"风险递增、可回滚"排序：

```
第 1 批：R-03（分析结果）    —— 已有缓存，迁移即验证缓存层；同时修失效 bug
第 2 批：R-01（数据源列表）  —— 范围清晰，失效点明确（Desired 更新处）
第 3 批：R-02（概览聚合）    —— 收益最高，但需确认 TTL 与陈旧容忍度
第 4 批：R-04（评论列表）    —— 需先压测键空间
（不做）R-05 / R-06 / R-07 / R-08 ~ R-11
```

---

## 6. 每个候选必须补齐的 7 项（迁移准入条件）

任何一类缓存进入实施前，必须在任务卡里写清：

1. 缓存 Key（版本化，如 `cp:insight:v1:source:list`）；
2. 缓存数据结构（JSON schema）；
3. TTL（含抖动）；
4. 失效触发点（哪个写操作之后删哪个 Key）；
5. 穿透保护（空值缓存 + 短 TTL，且不得把"无权限"缓存成"不存在"）；
6. 击穿保护（互斥加载或逻辑过期）；
7. 降级行为（Redis 不可用时回源 MySQL，不得抛错给用户）。

缺任何一项，不进入实施。
