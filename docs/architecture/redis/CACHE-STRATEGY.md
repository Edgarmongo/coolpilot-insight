# 缓存策略（CACHE-STRATEGY）

> 状态：设计稿（对应 `CACHE-CANDIDATE-ANALYSIS.md` 的 R-01 ~ R-04）
> 原则：**每一类缓存都必须写全 7 项**（Key / 结构 / TTL / 失效 / 穿透 / 击穿 / 降级），缺一项不实施

---

## 1. R-03 分析结果（词云 / 桑基图 / 主题）—— 第 1 批迁移

| 项 | 内容 |
|---|---|
| Key | `cp:insight:v1:analysis:{wordcloud\|sankey\|topic}:{videoId}` |
| 结构 | 词云/桑基图为 JSON 数组；主题为纯字符串 |
| TTL | 5 分钟 + 0~30s 抖动 |
| 失效 | 视频统计刷新（`AnalysisServiceImpl` 汇总入口）与清洗成功后，按 `analysis:` 前缀删除 |
| 穿透 | 结果确实为空时，缓存空数组 30 秒（**不要缓存 60 分钟**） |
| 击穿 | 单飞：同一 Key 只允许一个线程回源，其余等待 ≤200ms 后降级直查 |
| 降级 | Redis 不可用 → 直接计算并返回（等价于当前无缓存行为） |
| 测试 | 命中/过期/前缀失效/Redis 断开四类用例 |

**为什么要第 1 批**：对象现成、语义已知，且能顺带修掉"前缀失效不生效"的缺陷。
迁移后必须验证：**改了数据，5 秒内能看到新结果**（现在要等 5 分钟）。

## 2. R-01 数据源列表 —— 第 2 批

| 项 | 内容 |
|---|---|
| Key | `cp:insight:v1:source:list`、`cp:insight:v1:source:capabilities:{code}` |
| 结构 | 列表 / 三态明细（Desired / Observed / Effective）的 JSON |
| TTL | 5 分钟 + 抖动 |
| 失效 | **Desired 更新成功后**（`SourceCapabilityService` 写入口）删除 `source:` 前缀；数据源状态变更同理 |
| 穿透 | 不存在的 `code` → 短 TTL 空值（30s），**且不得把"无权限"缓存成"不存在"** |
| 击穿 | 单飞 |
| 降级 | 回源 DB + 快照 |
| 测试 | 更新 Desired 后立即读取必须看到新值（这是本类缓存最关键的断言） |

**特别注意**：能力三态里的 `Effective` 依赖 Observed 快照（TTL 60s）。
把三态整体缓存 5 分钟，会让"能力刚变成可执行"延迟最多 5 分钟才在页面生效。
→ **建议只缓存 `Desired` 的解析结果，`Effective` 每次按快照实时推导**，
或把这类 Key 的 TTL 压到 ≤60 秒。

## 3. R-02 概览聚合 —— 第 3 批（收益最高）

| 项 | 内容 |
|---|---|
| Key | `cp:insight:v1:overview:summary`（可按 `userId`/角色分片，见下） |
| 结构 | 概览对象：视频数、评论数、用户数、待复核、14 天趋势、痛点 Top12、Top10 视频 |
| TTL | 5 分钟 + 抖动 |
| 失效 | **纯 TTL**（不做主动失效）：聚合来源分散在采集/清洗/分析多处在写，逐个挂钩子成本高且易漏 |
| 穿透 | 该接口永远返回对象，无穿透问题 |
| 击穿 | 单飞（聚合最重，多个并发回源代价高） |
| 降级 | 直查 |
| 测试 | 数据变更后最多 5 分钟陈旧，且页面不报错 |

**分片要求**：概览含"待复核"等与用户相关的计数。若按用户过滤，Key 必须带用户维度
（`overview:summary:u{userId}`），否则会串数据——**这是最容易犯的错**。

## 4. R-04 评论列表分页 —— 第 4 批（需先压测）

| 项 | 内容 |
|---|---|
| Key | `cp:insight:v1:comment:page:{videoId}:{page}:{size}:{filterHash}` |
| 结构 | 分页对象（records + total） |
| TTL | 60 秒 |
| 失效 | 纯 TTL（清洗入库频繁，主动失效会打穿） |
| 穿透 | 不缓存"空页"以外的空结果；页码越界直接返回空，不写缓存 |
| 击穿 | 单飞 + 短 TTL |
| 降级 | 直查 |
| 测试 | 键空间规模（视频数 × 页码 × 筛选组合）必须实测后再定 TTL |

**风险**：评论列表参数组合多，键空间容易膨胀到触发 `allkeys-lru` 淘汰，
把真正有价值的聚合结果挤出去。**因此放在最后一批，且必须先有键空间估算。**

## 5. 三类典型问题（统一处理策略）

### 5.1 缓存穿透

- 对"确实不存在"的结果缓存空值，TTL ≤30 秒；
- **禁止**把"无权限访问"缓存成"数据不存在"（会造成越权判断错误，且难以察觉）；
- 对明显非法的入参（如负页码）直接拒绝，不写缓存。

### 5.2 缓存击穿

- 热点 Key 使用**单飞**（同一 Key 同时只有一个线程回源）；
- 或采用逻辑过期（value 内带 `expireAt`，后台异步刷新）；
- 单飞的等待上限必须小于业务超时，等不到就降级直查，不排队。

### 5.3 缓存雪崩

- TTL 统一加 0~30s 随机抖动；
- 不同 domain 的 TTL 错开（source 5min / overview 5min / comment 1min）；
- 启动时不预热（避免重启瞬间集中回源），靠按需加载。

---

## 6. 失效纪律（最容易出错的地方）

1. **删除在事务提交之后**——事务内删除会因回滚留下不一致；
2. **只删不更**——并发写场景下"更新缓存"会被旧值覆盖；
3. **前缀删除必须真实生效**——用 `SCAN`，不用 `KEYS`，且由 `CacheKey` 生成前缀；
4. **跨 domain 不联动**：清洗成功 → 删 `analysis:` 与 `comment:`；采集完成 → 删 `comment:` 与 `overview:`。
   联动关系写进代码注释，不写在文档里就一定会漏。

---

## 7. 降级与回滚

### 7.1 降级（自动）

```
缓存调用 → 异常/超时 → 记 WARN + 计数 → 返回未命中 → 业务回源
连续失败 N 次 → 熔断 30s → 期间直接走 Noop
```

### 7.2 回滚（手动，无需改库）

| 手段 | 效果 |
|---|---|
| `CACHE_ENABLED=false` + 重启 | 全部缓存旁路，等价于当前行为 |
| 单独回滚某一类 | 保留 `NoopCacheService` 装配开关按 domain 控制（可选实现） |
| 清空 Redis | `FLUSHDB`（谨慎，需评审）——纯缓存，清空只影响性能 |

**回滚不需要数据库迁移**，这是本设计刻意的约束。

---

## 8. 验证方法（灰度必须有对照）

| 项 | 方法 |
|---|---|
| 正确性 | 同一请求，对比"走缓存"与"直查 DB"的结果（同 Key 双读，仅灰度期开启） |
| 收益 | 迁移前后 24h：接口 P95 延迟、MySQL `SHOW STATUS LIKE 'Questions'` 增量 |
| 命中率 | `cache.requests{result=hit/miss}` 与 Redis `keyspace_hits/misses` 双口径 |
| 降级 | 停 Redis 容器 → 核心接口仍 200，P95 上升但无错误 |
| 一致性 | 更新 Desired 后 5 秒内读到新值（R-01）、改数据后 5 秒内词云更新（R-03） |

**灰度的判据不是"看起来快了"，而是"命中率与延迟都有数字，且故障演练通过"。**
