> 复审对象：`需求设计（抖音多视频评论分析与可视化平台）.md`（926 行，产品早期形态）

## 0. 一句话结论

**这份需求文档已经不是"当前需求"，而是一份"早期设计记录"。**
它的问题不是写错了，而是**三条线同时过期**：

1. **写了但从未实现的**（Redis 两处、`analysis_result` 落库、游客只读概览）；
2. **实现了但设计已变**（去重键、角色模型、采集执行方式、数据表）；
3. **现在成为硬约束却完全没写的**（能力准入、证据绑定、审计、去重记忆、单副本）。

继续把它当"需求依据"会导致三类事故：按它去建 Redis（其实从没有过）、
按它去查 `analysis_result`（表根本不存在）、按它去理解权限（把 RBAC 当成两角色）。

## 2. 数据模型：3 张表 → 47 张

| 原设计 | 现状 | 说明 |
|---|---|---|
| `user` 6 字段，`password` | 11 字段，`password_hash` + `must_change_pwd` + `last_login_at` | 字段名与语义都变了 |

## 3. 清洗去重规则：原规则已不成立

| | 原需求 | 现状 |
|---|---|---|
| 去重键 | `(昵称 + 内容 + 日期)` 组合，保留最新 | `cid`（平台评论 ID）优先；无 cid 时用 `sha256(platform\|aweme\|uid\|date\|content[:120])[:40]` |
| 唯一约束 | 无（应用层去重） | `uk_platform_cid(platform,cid)` + `uk_platform_dedup(platform,dedup_key)` |
| 重复采集 | 未考虑 | 跨次去重记忆（`/internal/collection/dedup`），第二次采集 `collected=0` |
| 空内容行 | 直接剔除 | 除昵称必填外，**有 cid 的空内容回复保留**（否则永远重复采集） |

原规则的致命问题：**昵称可改、内容可编辑**，用它当去重键会产生大量"假新评论"。
现在的 cid 方案是需求层面的一次实质修正，原文档没有记录。

## 4. 流程核对

### 4.1 采集

| | 原设计 | 现状 |
|---|---|---|
| 执行方式 | `ProcessBuilder` 起 Python 脚本，后端轮询状态 | 独立采集服务（Flask + 进程内队列），Java 走 `POST /v1/jobs`，轮询作业状态 |
| 准入 | 无此概念 | **能力准入闸门**：未验证能力一律拒绝，覆盖全部执行入口 |
| 失败分类 | "采集中/已完成/失败" 三态 | 七类 `failure_type` + `errorCode` + 作业 `finishedReason` |

### 4.2 分析

| | 原设计 | 现状 |
|---|---|---|
| 计算方式 | 查 `analysis_result` 快照，命中则返回 | 实时聚合 + `MemoryCache` 5 分钟 |
| 缓存位置 | Redis，TTL 30 分钟 | 进程内 Map，TTL 5 分钟，**前缀失效有缺陷**（见 CP-REDIS-01 审计） |
| 分析深度 | 词典规则情感 | 词典基线 + LLM 评论级分析 + 视频级洞察 + 证据表 |

### 4.3 登录

| | 原设计 | 现状 |
|---|---|---|
| Token 存储 | Redis（key=token, TTL 24h） | 进程内 `TokenStore` → **重启全员掉线** |
| 角色 | `role` 0/1 | `sys_role` + `sys_permission` + `sys_menu` + `user_role` |

## 6. 原需求**没写**、但现在已是硬约束的（最重要的缺口）

这些是系统真正的"隐性需求"，原文档一条都没有：

| 约束 | 现状 | 为什么必须有 |
|---|---|---|
| 能力三态（Desired/Observed/Effective） | `CapabilityReconciler` + ADR-008 | 决定"这个能力能不能执行" |
| 执行准入唯一入口 | `AdmissionGatedCollectionClient` | 防止未验证能力被执行 |
| 证据 ↔ 实现绑定 | `implementationHash` 含函数源码哈希 | 改实现必须重验，否则证据失效 |
| 操作审计 | `audit_log`（23 个调用点） | 谁在什么时候做了什么 |
| 跨次去重记忆 | dedup API | 不重复打扰平台，`collected` 才有意义 |
| 单副本部署 | ADR-007 §4.2.1 | 进程内队列 + 共享 Chrome profile |
| 日志脱敏 | `redact.py` + 日志清理 | 昵称/抖音号/IP/正文不进日志 |

**这些约束一条都没进需求文档**，却比原文档里的大部分条目更"硬"。

## 8. 对照新定位，需求**根本缺失**的部分

`PRODUCT-VISION` 的五个核心问题里，当前系统只覆盖了前两个：

| 问题 | 覆盖度 | 缺什么 |
|---|---|---|
| 市场发生了什么 | ⚠️ 单视频/单话题，无行业视角 | 跨内容聚合、趋势检测、竞品对比 |
| 用户需要什么 | ⚠️ 有痛点抽取，无分类体系 | taxonomy、需求归类、消费意向 |
| 内容传播如何 | ❌ 只有点赞排序 | 传播路径、渠道对比、时间衰减 |
| 商业机会在哪 | ❌ 零实现 | 商品/价格/竞品/机会模型（ADR-010 未定） |
| 下一步做什么 | ❌ 报告是描述性，不是建议性 | 结论分级（事实/推断/建议）+ 证据锚点 |

## 9. 建议的处置

### 9.1 对这份文档

**降级为历史记录**，在文首加一行"已被 `PRODUCT-REQUIREMENTS` 取代"，
不再作为需求依据（内容仍有参考价值的地方：CSV 字段、情感词典思路、采集字段映射）。

### 9.2 新的需求基线怎么组织（建议，未实施）

不要重写一份"大而全"的需求书，按**可验收**的粒度组织：

```
需求条目 ID | 所属能力域 | 用户故事 | 验收标准（可测） | 现状 | 优先级
REQ-SRC-01  | 数据源     | 作为运营，我能看到每个能力的三态与拒绝原因 | 页面展示 Effective+reason；未验证能力无法执行 | ✅ | P0
REQ-COL-03  | 采集       | 作为运营，重复采集同一视频不应重复抓取 | 第二次 collected=0 | ✅ | P0
REQ-CLE-02  | 清洗       | 作为运营，清洗失败要能定位到行级原因 | 返回结构化摘要（当前只有 stdout） | ❌ | P0
REQ-INS-01  | 需求洞察   | 作为分析者，痛点要能归入可配置分类 | taxonomy 可配置，结论带证据 | ❌ | P1
REQ-BIZ-01  | 商业洞察   | 作为分析者，能看到商品价格带与竞品分布 | 需 ADR-010 建模 | ❌ | P2
```

每条必须带"验收标准"，否则又会变成下一份"写了但没人能判定是否实现"的文档。

### 9.3 顺序建议

1. 先把旧文档标注为历史（1 行改动，零风险）；
2. 再写 `PRODUCT-REQUIREMENTS.md`，**只覆盖阶段一 + 阶段二**（P0/P1），不一次性写完五个阶段；
3. 商业洞察域等 ADR-010 决策后单独补，不在需求基线里先画饼。
